# 実験計画の吟味：貼られた計画（フェーズ1〜4）と、これまでの実験

このページは、次の 2 つを突き合わせた結果です。

- **計画**：貼られた「完全版・実験指示書」（実験 0、A〜H、FINAL）
- **これまでの実験**：`rds-proxy-go-performance` で実施済みの結果（Aurora MySQL 2〜4 vCPU、RDS Proxy、Go の `database/sql`）

> 前提：実験は本番の 1/10 規模（Aurora の `max_connections=100`）で、多くの条件は 1 回しか測っていません。
> 「実測」と書いたものも、規模や回数の制約があります。

## 1. 先に結論（3 行）

1. 計画の 11 実験のうち、**4 つは実施済み**（0、A、D、G の一部）、**2 つは途中**（F、B）、**5 つは未実施**（C、E、G の残り、H、FINAL）です。
2. 計画の中に、**これまでの実測と食い違う前提が 4 つ**あります（§3）。そのまま実装すると、誤った結論になるおそれがあります。
3. **「最終的なベスト設定」のコード例には、実測で失敗した書き方が含まれています**（§4）。

## 3. 計画の前提が、これまでの実測と食い違う点

### ① 「ローテーション中のエラー率 0%」は、そのままでは成り立たない（実験 D）

- 回転の直後に、新規ログインが**約 50 秒間、新旧どちらのパスワードでも失敗した**run があります（その間にクエリ 7 件が失敗）。長さは run ごとにばらつきました。
- 計画の合格条件を「エラー 0%」にすると、この窓で不合格になります。「窓の長さ」と「リトライで吸収できるか」を、合格条件にするほうが現実的です。
- GET_LOCK 用の専用接続は、プールの外にあるため、**入れ替わらず、古い認証情報のまま残りました**（6 本）。

### ② 「`SET time_zone` で永続ピン留め」は、実測では確認できていない（実験 G-3）

- セッションごとに `time_zone` を変えた実験（12 本）では、**ピン留めは 0 本**でした。
- `SET @v`（ユーザー変数）は、ピン留めされても、**Aurora の接続数を増やしませんでした**。
- つまり、計画の「SET はピン留めの原因 → 避ける」は、少なくとも `time_zone` では裏づけがありません。実験 G-3 は、「どの SET が、どれだけ接続を占有するか」を調べる形に直すのが妥当です。

### ③ 「RDS Proxy で DB 接続が大きく圧縮される」は、まだ見えていない（実験 E）

- クライアント 27〜50 本に対して、Proxy→Aurora は 33〜46 本で、**圧縮されていません**。
- 理由の候補：クエリが 50 ms と長く、同時に動く数が多い／前の実験の残りが混ざった。どちらも未切り分けです。
- 圧縮率は「外部 API 待ちの間、DB 接続を手放しているか」に依存します。実験 E では、**待ち時間中にトランザクションを持たないこと**を条件に入れます。

### ④ 実験 B の観測指標が、Go 側だけでは意味が薄い

- 「スパイク終了後に `OpenConnections` が MaxIdle 水準へ縮む」は、`database/sql` の仕様どおりに起きるので、確かめる価値が小さいです。
- 本当に知りたいのは、**Proxy 側の `DatabaseConnections` がバースト後にどう動くか**です。バースト後に 25 本が約 5 分残った実測があり、ここを測るべきです。

## 4. 「最終的なベスト設定」のコード例の問題点

| コード例の記述 | 問題 | 根拠 |
|---|---|---|
| DSN に `user:pass@...` を固定で書く | 回転後に、接続を入れ替えると**新規接続が全部失敗し、プールが空になって復旧しない**（失敗 58,599 回） | 実験 D（実測、1 回） |
| `loc=Asia%2FTokyo` で `time_zone` の `SET` を避ける | `loc` は、Go 側で時刻を解釈する設定です。**DB のセッションの `time_zone` は変えません**。サーバー側の時刻が必要なら、別の方法が要ります | ドライバの仕様（要確認：実験で確かめる） |
| `SetConnMaxLifetime(30 分)` で、回転に追従 | 回転後に古い接続が消えるまで、最大 30 分かかる。2 分なら、中央値 95 秒、最大 125 秒で入れ替わった | 実験 D（実測、1 回） |
| `SetMaxIdleConns` は「普段の同時数」 | 方向は合っている。実測では、**同時使用数の中央値の 1.5 倍**ぐらいが、遅延の頭打ち点（2〜5 本）に収まった | 実験 A（実測） |
| `SetConnMaxIdleTime(3 分)` が安全 | 値の大小より、**ワーカーの実行間隔より長いか**が重要。30 秒おきのワーカーなら、3 分で問題ない | 実験 F（未実行、試算） |
| `SetMaxOpenConns` ＝ 限界 ÷ コンテナ数 | 方向は合っている。1 コンテナに集中する場合は、**限界の 2 倍（膝の 2 倍）÷ コンテナ数**を使う。2 倍にしても、処理量は落ちなかった | 実験 0（実測） |

「ベスト設定」は、**実験 FINAL の結果が出るまで、推奨設定ではなく仮説**として扱うのが安全です。

## 5. 計画に足したほうがよいこと

1. **実験の間に、約 6 分待つ**。Proxy の裏の接続が約 5〜6 分残るため、待たないと、前の実験の影響が次に混ざります（実験 B の結論が暫定になった原因です）。
2. **各条件を、順序を入れ替えて、複数回**行う。1 回では、ばらつきがわかりません。
3. **生データを保存する**（CloudWatch の JSON、`db.Stats()` のログ）。
4. **負荷を出す側の CPU を確認する**。ここが律速していないことを、毎回確かめます。
5. **各ステップは 10 秒より長くする**。階段負荷（実験 0）で、Proxy の裏の接続が追いつく前に次へ進むおそれがあります。
6. `MaxOpen=150` は、Aurora の `max_connections=100` を超えます。実験 0 の上限は、**Proxy の上限（80）と、Aurora の上限（100）を意識して**決めます。
7. PostgreSQL の確認 SQL は、今の環境（Aurora MySQL）では使いません。MySQL に絞ります。

## 6. 推奨する進め方

| 順 | 内容 | 理由 |
|---|---|---|
| 1 | 共通ロガー（`db.Stats()` を 500 ms ごと）を作る | 全実験で使う |
| 2 | 実験 G-2（GORM の `PrepareStmt`）、G-4（長いトランザクション）を実施 | 未実施で、本番で踏みやすい |
| 3 | 実験 D を、各 3 回に増やす | 窓の長さと原因の切り分け |
| 4 | 実験 F、H | 設定値（IdleTime、Lifetime）の根拠になる |
| 5 | 実験 B、E を、待ち時間を取って再実験 | 結論が暫定のため |
| 6 | 実験 C | 本番の「サイト単位」に近い |
| 7 | 実験 FINAL（§4 のコードを直したうえで） | 最後に統合 |

実験 0 と A は、実施済みの結果を、新しい条件（4 → 128 本、バースト型）で足す程度で十分です。
