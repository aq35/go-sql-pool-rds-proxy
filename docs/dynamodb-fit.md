# DynamoDB の向き不向き(このリポジトリの調査のまとめ)

**状態: 試算と一般的な使い方の整理。DynamoDB の実験は行っていない(実験コードは `archive/realtime-sync/`)。**
単価は AWS の価格 API から取得(`scripts/fetch_pricing.py` → `lab/pricing.json`、東京、取得日 2026-11-15、オンデマンド)。

## 向くもの / 向かないもの

| 向く | 向かない |
|---|---|
| キーで引く(ID を指定して取る)検索が中心 | JOIN、集計、条件を組み合わせた検索など、複雑な検索 |
| 書き込みが少ない、または変化したときだけ書く | 全件を、毎秒、定常的に書き換える |
| 読み取りが中心、または負荷が急に大きく波打つ | 書き込みが、定常的に多い |
| 件数が非常に多く、水平に広げたい | 複数のテーブルをまたぐ整合性(トランザクション)が重要 |
| 1 項目が小さい(1KB 以内) | 1 項目が大きく、毎回、全体を書き換える(1KB ごとに課金) |

## 費用の考え方(オンデマンド)

- **書き込み: $0.715 / 100 万ユニット。1 項目あたり、1KB ごとに 1 ユニット(切り上げ)。** 1 ユニット/秒を 1 か月(259 万秒)続けると、約 **$1.85**。
- **読み取り: $0.1425 / 100 万ユニット。** 4KB ごとに 1 ユニット(結果整合なら半分)。1 ユニット/秒を 1 か月続けると約 $0.37。
- 境界(項目)を細かく分けるほど、**1KB への切り上げの無駄**と、**問い合わせの回数**が増える。まとめると安くなるが、書き込みの量(KB)そのものは、あまり減らない。

## Aurora との分岐点(目安)

- Aurora r6g.large(月約 $225、東京、$0.313/時)と同額になる書き込み量: **約 120 ユニット/秒**(約 120KB/秒)。r6g.xlarge(月約 $450)なら約 240。
- これより多く書き続けるなら、Aurora のインスタンスのほうが安い(**Aurora がその量を捌けて、そのシステム専用である場合**)。
- Aurora の請求対象 I/O($0.24 / 100 万リクエスト)は、書き込みが多いと大きくなる。**未実測**。I/O 込みの料金体系(I/O-Optimized、r6g.large で $0.407/時)のほうが安くなる場合もある。

## 例(試算。実測ではない)

| 条件 | DynamoDB の書き込み | DynamoDB の月額 | 判断 |
|---|---|---|---|
| 200 サイト × 状態 10 件、毎秒全件(状態ごとに 1 項目) | 約 2,000 ユニット/秒 | 約 $3,700 | Aurora |
| 200 サイト、サイトごとに 1 項目(約 4KB)、毎秒全件 | 約 800 ユニット/秒 | 約 $1,500 | Aurora |
| ロボット 600 台、1 台 1 項目(1KB 以内)、毎秒 | 600 ユニット/秒 | 約 $1,110 | Aurora(I/O の実測次第) |
| ロボット 600 台、変化した台だけ(10%) | 60 ユニット/秒 | 約 $110 | DynamoDB も候補 |

## 判断の手順

1. **書き込みの量を数える**: (1 秒あたりの書き込み件数) × (1 項目のサイズ KB、切り上げ)。変化したものだけ書けるなら、その割合を掛ける。
2. 120 ユニット/秒(r6g.large との比較)を、**大きく超えるなら Aurora**。
3. 複雑な検索、JOIN、トランザクションが要るなら、Aurora。
4. DynamoDB を選ぶなら、「変化した分だけ書く」ことと、プロビジョンド容量(負荷が一定の場合。単価は未取得)を検討する。
5. 1 秒ごとの全件取得(フロントのキャッシュ更新)が目的なら、**Go のメモリに最新状態を持つ**ことで、DB を読まない設計も検討する。
