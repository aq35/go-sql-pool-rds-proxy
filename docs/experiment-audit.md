# 実験の精査（監査メモ）

目的: 今回の実験の結論が、どこまで信頼できるかを明らかにし、次の実験の設計に反映する。
根拠は、保存済みの `results/` と、`client/run-all.sh` の実験定義。

## 重大度が高い

### A1. 実験間の待ち時間が、残留時間より短い
- 事実: クライアントがいなくなったあと、Proxy は裏の接続を約 5〜6 分保持する（`results/trigger/summary.txt`）。
- 実験間の待ち: idle 約 3 分、idleh 約 2 分、tls 約 1 分、exceed 7 分（`results/*/timeline.tsv` の「実行終了」と「窓の終了」の差）。
- 影響: 保存した `results/idle/idle-*.json` では、実験の終了 3 分後でも DatabaseConnections が 41〜45。次の実験は、前の残留から始まる。
- 対策: 各実験の開始前に、**DatabaseConnections が下限（5）に戻ったことを確認してから始める**（固定の待ち時間ではなく、条件で待つ）。開始時の値を、結果に記録する。

### A2. 生データが残っていない
- `results/idleh/` に JSON がなく、`results/idle/*.client.txt` は空（88 バイト）。
- 対策: 実験ごとに、クライアントログ、CloudWatch の JSON、引数、コミットを、同じフォルダに保存する。インフラを削除する前に、保存の完了を確認する手順にする。

## 重大度が中

### B1. 各条件 1 回のみ、実行順が固定
- ばらつきがわからない。時間帯（t4g の CPU クレジット、Proxy の状態）の影響を、条件の差と分けられない。
- 対策: 各条件を 3 回、順番を入れ替えて実行する。差が、ばらつきの範囲に収まるかを報告する。

### B2. 負荷生成側が律速している可能性
- `SELECT SLEEP(0.05)` の平均が約 130ms。原因は未解明（t4g.micro の CPU が候補）。
- 対策: 負荷生成側の CPU 使用率を同時に記録する。律速しているなら、大きめのインスタンスにする。

### B3. 指標の取り方が実験ごとに違う
- `collect.sh` は ClientConnections を `Sum` で取る（ゲージ系は `Maximum`）。
- `ClientConnections` が実ソケット数と合わない（12 本で 6 など）。
- 対策: 指標ごとに統計（Maximum / Sum / Average）を、定義ファイルで 1 か所に固定する。クライアント側のソケット数を、必ず同時に記録して、突き合わせる。

### B4. ピン留めの積み上がりを、継続的な負荷で確認していない
- exceed は 10 分（0.25 本/秒）で、本番の「毎秒数十回」とは桁が違う。
- 対策: 開閉の頻度を 2 桁変える実験（0.25、2.5、25 本/秒）を追加する。上限（Proxy の 80 本）に達する条件も入れる。

## 重大度が低い

- C1. `steady-settz` は、time_zone が Proxy に追跡されると、ピン留めもプールの分離も起きない。「セッション設定の違いで分かれない」と言える条件にはなっていない。ユーザーを分けた比較が必要。
- C2. 実験は admin ユーザー、TLS なしが多い（trigger、exceed）。本番は、アプリ用のユーザー、TLS あり。
- C3. Aurora は t4g.medium（バースト対応）。CPU クレジットの残量で、CPU の見え方が変わる。
- C4. 本番との規模の差（1/10）。接続数の上限（Proxy 80 本）に、バーストが届かなかった。

## 次の実験の設計への反映

1. 各実験の前後に「下限に戻るまで待つ」を入れる（A1）。
2. 結果の保存を、実験の一部にする（A2）。
3. 各条件を 3 回、順番をずらして実行する（B1）。
4. 指標の定義を 1 か所にまとめる（B3）。
5. 仮説と、結果の読み方（何が出たら、仮説が正しいか）を、実験の定義に書く。

## 対応状況（テンプレート化で入れたもの）

| 項目 | 対応 | 状態 |

| C1・C2・C4 | 未対応（ユーザー別プール、アプリ用ユーザー + TLS、規模） | 未 |
