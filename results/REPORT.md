# 実験結果: Go の接続プール × RDS Proxy × Aurora MySQL(2026-11-16)

計画は [docs/EXPERIMENT_PLAN.md](../docs/EXPERIMENT_PLAN.md)。この文書は、その実行結果。

## 条件と、読むときの注意

- Aurora MySQL `max_connections=100`、**db.r6g.large(2 vCPU)**、RDS Proxy(MaxConnectionsPercent 80、MaxIdleConnectionsPercent 10)。EC2 の Go クライアントから、東京リージョンで接続。本番の 1/10 規模。
- 各条件の繰り返しは **2〜3 回**(`lifecycle-sync` は 1 回)。範囲 [最小–最大] を併記した。範囲が重なる差は、結論にしない。
- **CloudWatch(1 分刻み)の列は、すべて、前後の run が混ざる。** run の間隔が約 40 秒のため。CPU は、飽和しているはずの run で 36% などと出たので、結論に使わない(先行調査の `capacity` の結果を使う)。`proxy_pinned_max`、`proxy_intx_max` なども、同じ理由で、直前の run の影響を受けうる(ただし、ピン留めされた run の直後の run で 0 だった例があり、ピン留めは接続を閉じるとすぐ消えるとみられる)。次の実行(`patterns-v2`)で、CPU は 1 秒値(Enhanced Monitoring)に置き換える。
- 遅延を読む実験は、run の間の「接続数が下限に戻るまでの待ち」を省いた。そのため、**Proxy の `DatabaseConnections` は読まない**(前の run の残りを含む)。
- `ClientConnections` は、実ソケット数より少なく出る(10 本で 5〜8)。ピン留めの数が、見かけ上、クライアント数に近くなる。**原因の有力な候補(未検証)**: この実験は、接続数のゲージをすべて `Maximum` で取っていた。AWS のドキュメントは、これらのゲージの推奨統計を **`Sum`** とし、「proxy は複数のインスタンスで提供されることがあり、指標はインスタンスごとに出る」と書いている(`docs/metrics.md`)。`Maximum` は、最も大きい 1 インスタンスの値しか見ない。**そうなら、`DatabaseConnections`、ピン留めの数、`InTransaction` も、実際より少なく出ている。** **スモークテスト(同日)で確認できた**: 同じ run で、`ClientConnections` は `Maximum` = 7、`Sum` = **10**(Go 側が数えた接続数 = 10 と一致)、`Average` = 5.0。Proxy は 2 ノードで、`Maximum` は片方だけを見ていた(詳細と注意: `docs/metrics.md`。n=1)。**この文書の Proxy の接続数の値は、下限として読む**(約 3 割少ない可能性)。特に A1(下限の 5 本)は、**Proxy 全体では 10 本**だった(使われたあと、クライアントがいなくても `Sum` = 10(`Max` = 5)で、1 時間以上安定。設定の `MaxIdleConnectionsPercent` 10% × `max_connections` 100 と一致するとみられる。未使用の Proxy は 0。`docs/metrics.md`)。
- 先行調査(実験 0、A、B、D)は別リポジトリでの結果で、ここには含めない。
- **版の注意**: この文書の結果は、**MySQL ドライバ v1.8.1、gorm v1.25.12、EC2 の `dnf` の Go(版は未記録)**で測った。コードは、その後、**Go 1.27.4、ドライバ v1.10.1、gorm v1.31.2** に更新した(`docs/known-vulnerabilities.md` §4)。以後の run は、`meta.json` の `go_version` / `go_deps` に版が残る。更新前後の結果は、傾向としてのみ比べる。

## 2. GORM: MaxOpenConns が小さいと固まる書き方(X3、3 回)

| 書き方 | MaxOpen=1 | MaxOpen=2 |
|---|---|---|
| トランザクション中に `tx` で別のクエリ | 完了 | 完了 |
| トランザクション中に、`tx` ではなく **`db` で別のクエリ** | **固まる(3 秒でタイムアウト)** | 完了 |
| `Preload` を 2 つ | 完了 | 完了 |
| 関連(子テーブル)を含む `Create` | 完了 | 完了 |
| `BeforeCreate` フックで `tx` を使う | 完了 | 完了 |
| `BeforeCreate` フックで、**グローバルの `db` を使う** | **固まる(3 秒でタイムアウト)** | 完了 |

- 仮説どおり。**`Preload` や関連つきの `Create` は、それだけでは固まらない。** 固まるのは、トランザクションの中で、そのトランザクションを使わずに、別の接続を要求したとき。
- 結論(実測の範囲): **MaxOpenConns は 2 以上にする。** 1 では、「`db` で別のクエリ」を 1 か所書いただけで、アプリが固まる。(推論で、未測定: 2 でも、同じ書き方が 2 つ同時に走れば、同じ理由で固まるはず。)根本の対処は、トランザクションの中では `tx` を使うこと。

## 3. 一斉寿命(スタンピード、実験 H、3 回)

32 本のプール、ConnMaxLifetime 60 秒、5 分間、TLS・別 AZ。

| | 同時に作る(sync) | 時間をずらして作る(staggered) |
|---|---|---|
| 1 秒あたりの新規接続の最大 | **30**(22〜31) | **6**(4〜6) |
| その秒の p99(最初の 5 秒を除く) | **71 ms**(41〜76) | **25 ms**(24〜27) |
| 全期間の p99 | 13.3 ms | 8.3 ms |
| 全期間の p50 | 6.0 ms | 5.9 ms |

- 同時に作ると、寿命の秒(約 60 秒ごと)に、32 本がほぼ一斉に作り直され、その秒の p99 が約 3 倍になった。ずらすと、約 1/3 に下がる(**なくなるわけではない**: 25 ms は、全期間の p99 の 8.3 ms より高い)。
- **条件がそろっていない点**: staggered は、ワーカーの開始を最大 60 秒ずらすので、総クエリ数が約 9% 少ない(15.6 万 対 17.1 万)。また、staggered の 1 秒あたりの新規接続の最大が 6 本なのは、理論値(32 本 ÷ 60 秒 ≒ 0.5 本)より多く、**原因は未確認**。
- **影響の大きさ**: 悪化した 1 秒の p99 が 71 ms。全期間の p50 は変わらない。このスケール(32 本、TLS・別 AZ)では、実害は小さい。接続の数が増えると、大きくなる可能性がある(未測定)。
- 対処: ConnMaxLifetime を、**起動時刻をずらす、または、ばらつきを持たせる**。Go の標準にはジッターがないので、起動を分散させるか、定期的にプールの入れ替えをずらす。

## 4. ピン留めされる設定(実験 G、2 回、10 ワーカー、200 秒)

Go 側で、どの設定が RDS Proxy のセッションをピン留めするか。`Com_stmt_prepare` は Aurora 側の増分。

| 条件 | ピン留め(最大) | `Com_stmt_prepare` の増分 | クエリ数 |
|---|---|---|---|
| base(`interpolateParams=true`、PrepareStmt なし) | **0** | 0 | 33,312 |
| G-1 `interpolateParams=false`(Go の既定) | **6**(= ClientConnections の最大) | **30,456**(クエリごとに 1 回) | 30,456 |
| G-2 `interpolateParams=true` + GORM `PrepareStmt: true` | **6.5**(= ClientConnections) | 10(接続ごとに 1 回) | 33,028 |
| G-3 DSN の `time_zone` | **0** | 0 | 33,038 |
| G-3 DSN の `sql_mode` | **0** | 0 | 32,389 |
| `loc` だけ(`SET` なし) | **0** | 0 | 33,021 |
| G-4 トランザクション内で 200 ms 待つ | **0**(`InTransaction` は 6.5) | 0 | 6,880 |

- **ピン留めは、サーバー側プリペアドステートメントで起きる。** G-1 と G-2 は、どちらも、ピン留めが最大 6〜6.5 本で、その時の `ClientConnections` の最大(6〜6.5)と同じだった。ワーカーは 10 本なので、**「プール全体がピン留め」とまでは断定できない**(`ClientConnections` が実数より少なく出るため、実際は最大 10 本の可能性がある。数は未確認)。
- **G-1 は、1 クエリごとに prepare が走る**(クエリ数と増分が一致)。`interpolateParams=false` のままだと、パラメータ付きのクエリが、すべて prepare になる。
- **G-3(`time_zone`、`sql_mode` を DSN で設定)は、ピン留めされなかった。** 計画の「`SET` は永続ピン留めの原因」は、この 2 つについては成り立たなかった。ほかの `SET` は未測定。
- **`loc` は、`SET` を送らない**(Aurora 側の `Com_stmt_prepare` が 0、ピン留めが 0)。「サーバーの `time_zone` が変わらない」ことは、**AWS の run では確認していない**(ローカルの MySQL では、`loc` だけだと `SYSTEM`、DSN の `time_zone` だと `+09:00` を確認した。`patterns-v2` で、Aurora でも記録する)。サーバー側の `time_zone` が要るなら、DSN の `time_zone`(今回、ピン留めされなかった)を使う。
- **G-4 の長いトランザクションは、ピン留めではない**(0)。ただし、トランザクションの間、接続が専有される(`InTransaction` が 6.5)。クエリ数が少ないのは、各回に 200 ms の待ちを入れた設計どおり(悪化ではない)。トランザクションの中で外部 API を待つと、その間、接続が専有されるので、同時に捌ける数は、MaxOpenConns ÷ 待ち時間に制限される。
- これは、1 規模・短時間(200 秒)・各 2 回の結果。Aurora の `Com_stmt_prepare` の増分は、Proxy を通らない専用の接続で測ったので、信頼できる。

## 5. 直列 vs 並列(X1、2 回)

1 リクエストが、5 つのクエリ(CPU が重い mix)を実行。到着はポアソン、1 回 60 秒。リクエスト/秒の上限は、先行調査の 2 vCPU の限界(約 386 QPS)から、約 77。

| MaxOpen | 到着(req/s) | p50(直列 / 並列) | p99(直列 / 並列) | プール待ちの合計(直列 / 並列) |
|---|---|---|---|---|
| 20 | 30 | 39 / **20** ms | 76 / **57** ms | 0 / 0.3 秒 |
| 20 | 55 | 54 / **32** ms | 245 / **186** ms | 1.1 / 55.8 秒 |
| 20 | 70 | 98 / **51** ms | 1,341 / **542** ms | 307 / 681 秒 |
| 6 | 30 | 40 / **20** ms | 119 / **74** ms | 1.8 / 43 秒 |
| 6 | 55 | 56 / **33** ms | **207** / 280 ms | 40 / 319 秒 |
| 6 | 70 | 92 / **74** ms | **621** / 957 ms | 348 / 1,689 秒 |

- **p50 は、すべての条件で、並列が速い。**
- **p99(裏返るのは、MaxOpen=6 で、55 req/s 以上)**: 並列のほうが悪くなった。プール待ちの合計は、並列が直列の 8 倍(55 req/s)と 5 倍(70 req/s)。
- **MaxOpen=20 では、70 req/s(限界の約 90%)まで、並列が p50・p99 とも速かった。** 裏返りは、プールが小さいときだけ。
- 仮説のうち、「並列は、CPU が飽和に近づくと p99 が悪化し、MaxOpen が小さいと接続待ちで、直列より悪くなる」は、**MaxOpen=6 の p99 で支持**された。「CPU が飽和すると、どちらも処理量が増えない」は、この実験では確認していない(CPU の列が信頼できないため)。
- 注意: 「プール待ちの合計」は、`db.Stats().WaitDuration` の差で、**待った全リクエストの待ち時間の合計**(実時間ではない)。各条件は 2 回で、p99 の範囲が重なる条件もある。「限界の約 90%」は、先行調査の 386 QPS を基にした推定で、この実験で CPU を直接測ったものではない。
- 設計への示唆: 並列にするなら、**MaxOpen が、同時に走るリクエスト数 × 並列数に足りているか**を確かめる。足りないなら、並列は、p99 を悪くする。

## 6. タイムアウトの連鎖(X2、2 回)

1 クエリ(CPU が重い、約 5 ms)を、ポアソン到着で、90 秒。MaxOpen=32。

| 到着(qps) | タイムアウト | 成功/秒 | タイムアウト数 | 新規接続数 | p50 / p99 |
|---|---|---|---|---|---|
| 300(限界の約 78%) | なし | 302 | 0 | 32 | 11 / 265 ms |
| 300 | 200 ms | 298 | 16 | 45 | 11 / 88 ms |
| 300 | 50 ms | 295 | 556 | 680 | 11 / 41 ms |
| 300 | **20 ms** | **266** | 2,848 | **3,186** | 9 / 20 ms |
| 460(限界の約 119%) | なし | 402 | 0 | 32 | **1,054** / 6,489 ms(5,200 件を取りこぼし) |
| 460 | 200 ms | 332 | 11,539 | 8,605 | 108 / 199 ms |
| 460 | 50 ms | 309 | 13,651 | 13,518 | 35 / 51 ms |
| 460 | **20 ms** | **217** | 21,694 | **25,234** | 13 / 21 ms |

- **タイムアウトのたびに、接続が 1 本閉じられ、作り直される。** 新規接続数は、タイムアウト数にほぼ比例する(0.75〜1.2 倍)。
- **限界の 78% でも、20 ms のタイムアウトは、成功/秒を約 12% 下げた**(302 → 266)。タイムアウトが短いほど、接続の作り直しが増える。(「タイムアウトのたびに、接続が閉じられる」は、ドライバの仕様と、新規接続数がタイムアウト数に近いことからの推定で、個々の接続は追跡していない。)
- **説明できていない値**: タイムアウトなしの r300 で、p99 が 265 ms と大きい(p50 は 11 ms)。限界の 78% としては大きく、原因は未確認(Aurora の一時的な詰まり、ポアソン到着の偏り、など)。
- **限界を超える(119%)と、タイムアウトが短いほど、成功/秒は下がる**(402 → 332 → 309 → 217)。ただし、「なし」の 402 件は、**p50 が 1 秒を超える**(多くはユーザーにとって遅すぎる)ので、実質の成功は、これより少ない。
- **「クライアントが切断した後も、Aurora でクエリが走り続ける」は、今回は確認できなかった。** Aurora 側で実行中のクエリの最大は、どの条件でも 4〜6。クエリが約 5 ms と短く、切断前に終わるため。長いクエリでは、別途測る必要がある。
- エラーは、`use of closed network connection` が 1 件のみ。

## 7. アイドルタイムアウトの競合(実験 F、**1 回のみ**)

Proxy の IdleClientTimeout を 60 秒にし、各ワーカーが約 60 秒おきにクエリ。

| ConnMaxIdleTime | p99 | 平均 | エラー |
|---|---|---|---|
| なし | 12 ms | 9.3 ms | 0 |
| 30 秒 | 18 ms | 9.9 ms | 0 |
| 50 秒 | 23 ms | 9.6 ms | 0 |
| 90 秒 | 12 ms | 10.1 ms | 0 |

- **エラーは、どの条件でも 0。** 仮説の「`ConnMaxIdleTime` が IdleClientTimeout を超えると、`invalid connection` / `EOF` が出る」は、**この条件では再現しなかった**。go-sql-driver が、Proxy に切られた接続を検知して、透過的に再接続しているとみられる。
- 差は p99 だけ。ConnMaxIdleTime を、クエリの間隔(約 60 秒)より**短く**すると、毎回再接続になり、p99 が悪化した(12 → 18〜23 ms)。
- 1 回のみで、範囲がわからない。結論ではなく、傾向。
- 「ドライバが透過的に再接続している」は推測。ConnMaxIdleTime なし(Proxy に 60 秒で切られる)の p99 が、30 秒・50 秒より低い理由も、説明できていない。

## 8. ウォームアップ(X4、3 回、32 同時、TLS・別 AZ)

新しいプールに、32 本の `SELECT 1` を同時に流した、最初の波の遅延(10 試行の中央値)。

| | 温めない(cold) | `PingContext` を 32 並列で先に流す(warm) |
|---|---|---|
| 最初の波の p50 | **53.8 ms**(44.9〜94.9) | **7.1 ms**(7.0〜8.9) |
| 最初の波の最大 | **77 ms**(73〜146) | **10 ms**(10〜14) |
| 2 回目の波の p50(基準) | 6.9 ms | 7.4 ms |
| 温めるのにかかる時間(起動時のコスト) | 0 | **92 ms**(79〜99) |

- 温めないと、最初の波は、2 回目の波の約 8 倍遅い(約 47 ms の差)。温めると、2 回目と同じになる。
- コストは、起動時の約 92 ms。**オートスケールで立ち上がる直後の最初の波**を、なだらかにしたいなら、効果がある。
- 温めた接続を保つには、MaxIdleConns の枠が要る(先行調査では、2〜5 で頭打ち)。
- **この実験の限界**: 試行の間隔が 15 秒で、Proxy の裏の接続(Proxy→Aurora)は、前の試行から温まったまま。**Proxy 側も冷えた状態(本当のコールドスタート)の遅れは、測っていない。** クエリは `SELECT 1` で、実際のクエリではない。

## 10. 断定できないこと・不正確になりうる点(監査)

| # | 点 | 影響 | 対応 |

## 12. opt-v1(2026-11-17、Sum 主、15 実験・全 run 有効)の追加結果

出典: `results/_opt-v1-2026-11-17/`(CloudWatch は実験後に再取得)。各条件 1 回のものは傾向として読む。`proxy_condition=warm` の run は、前の run の接続が残る可能性がある。

### 12.1 ピン留めされる設定(pat-pin、10 ワーカー、各 1 回)

| 設定 | pinned Sum | 根拠・注意 |
|---|---|---|
| base | 0 | |
| `interpolateParams=false` | 10 | Aurora の prepare が 17,219 回(クエリごと)。pat-driver-ab でも v1.8.1 / v1.10.1 とも 10 |
| GORM `PrepareStmt` | 10 | prepare は接続ごとに 1 回(10 回)。pat-driver-ab でも同じ |
| `time_zone` を DSN で SET | **0** | 先行調査と一致。session の time_zone は +09:00 になっている |
| `sql_mode` を DSN で SET | **0** | |
| `sql_select_limit` / ユーザー変数 / `max_execution_time` を SET | 10 | 追跡できない変数は、ピン留めされる |
| `wait_timeout` を SET | **0** | |
| `autocommit=0` | pinned 0、InTransaction 10 | 接続が常にトランザクション内になる |
| 長いトランザクション | pinned 10、InTransaction 10 | **要確認**(下記) |
| `loc` だけ | 10 と出たが **疑わしい** | SET が走らないはず。直前の run が `prep-false` で、前後の run が混ざった可能性 |

- 窓の混ざりがあるため、1 回の run の pinned は断定しない。確度が高いのは Aurora 側の prepare 数と、0 になった変種(base、time_zone、sql_mode、wait_timeout)。
- 長いトランザクションがピン留めに出るかは、前後の run の影響を切り分けていない(要追試)。

### 12.2 ドライバ v1.8.1 と v1.10.1(pat-driver-ab)

- prepare 数、pinned、エラー(各 0)は、2 つの版で同じ。コールドの 1 回目は p50 15.4 ms(新)/ 12.7 ms(旧)、2 回目は 4.8 ms で、差は誤差の範囲。
- 切れた接続への再接続は、どちらの版も 1 回、エラーなしで行った(matrix の errors=1 は両方の版に出ている)。
- 結論: 前回の結果との差は、ドライバの版ではなく条件の違い。

### 12.3 一斉寿命(pat-stampede、ConnMaxLifetime=60 s、32 本)

| 条件 | 1 秒あたりの新規接続の最大 | 秒ごとの p99 の最大(ms) | 定常 p99(ms) |
|---|---|---|---|
| sync | 15 [14–16] | 113 [72–153] | 8.7 |
| staggered | 9.5 [9–10] | 79 [54–105] | 9.3 |
| lifetime=0 | 0 | 44 [38–50] | 9.1 |

- 新規接続の山は、staggered で約 1/3 減る。
- p99 のスパイクは sync > staggered の向きだが、範囲が重なる(2 回ずつ)。確定ではない。lifetime=0 にも 44 ms のスパイクがあり、寿命以外の揺らぎもある。
- 定常の p50 / p99 は 3 条件でほぼ同じ。

### 12.4 混在負荷(pat-mixed、サイト 10 / 40 × プール設定 × Web の流し方、各 1 回)

| 条件 | エラー | 全体 p99(ms) | Proxy の Aurora 接続 Sum | pinned Sum | idle で閉じた数 |
|---|---|---|---|---|---|
| 10 サイト、GORM 既定、直列 | 0 | 17.9 | 23 | 10 | 459 |
| 10 サイト、ルール値、直列 | 0 | 13.4 | 24 | 10 | 0 |
| 10 サイト、ルール値、並列 | 0 | 13.4 | 41 | 10 | 223 |
| 40 サイト、GORM 既定、直列 | 0 | 18.4 | 52 | 40 | 434 |
| 40 サイト、ルール値、直列 | 0 | 14.7 | 56 | 40 | 0 |
| 40 サイト、ルール値、並列 | 0 | 13.2 | **71** | 40 | 172 |

- サイトの GET_LOCK の専用接続は、1 サイト = pinned 1 本(10 → 10、40 → 40)。
- **40 サイト + 並列で、Aurora 接続が 71 本に達し、Proxy の上限 74 に近づく。** 本番の 10 倍規模(800 本)の説明として、「ピン留め + 並列」が有力。
- GORM 既定(MaxIdle 2)は、idle で閉じる接続が多い(約 450)が、この負荷では、p99 の悪化は +4 ms 程度で、エラーはない。
- 仮説「サイト 40 で待ちが増える」は、MaxOpen 22 のままでは pool_wait_count が 0 で、確認できなかった。

### 12.5 上限を超える接続数(exceed-cases)

- 40 本のバースト(burst)で、Proxy の Aurora 接続は Sum 54(クライアント Sum 40)。終了後、下限に戻るまで約 5.3 分。
- churn-prepared(prepare を繰り返す短命接続)は、クライアント Sum 13 に対し Aurora 接続 Sum 40 で、**DB−Client が 48**。短命でピン留めされる接続は、Aurora 側に残る。
- GET_LOCK を繰り返す churn-getlock は、下限 10 のまま。

### 12.6 未解決

- `SLEEP(0.5)` を Proxy 経由で流すと、Aurora 側で同時に動くクエリが約 10 本で頭打ちになる(Proxy は 32 本の接続を開いている)。直結との比較が必要。
- pat-limit の busy-clients は、ドライバの ReadTimeout(60 秒)が SLEEP(90 秒)より短く、無効。hold を 45 秒にして再実行が必要(再デプロイが必要)。
