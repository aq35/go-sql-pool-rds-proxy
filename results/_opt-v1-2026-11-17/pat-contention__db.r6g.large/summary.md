# pat-contention — db.r6g.large

**問い**: CPU が律速でないとき(ロック待ち、トランザクションの保持)、接続数(プールの大きさ)は、スループットに、どう効くか

**仮説**: 同じ行を更新する競合(hot-row)では、ワーカー数や、プールの大きさを増やしても、スループットは増えず(行ロックで直列化)、Aurora の CPU は低いまま、InUse は、プールいっぱいまで使われる。別々の行(spread-rows)では、スループットが、はるかに高い。トランザクションが接続を保持する(tx-hold)場合、スループットは、プールの大きさ ÷ 保持時間(リトルの法則)で決まり、プールを大きくすると、その分、増える。

**読み方**: hot-row-16 と spread-16 を比べる(同じ接続数で、ops_per_s が何倍違うか。aurora_cpu_p50 / max が低いか)。hot-row-64 が、hot-row-16 より増えないか。tx-hold-pool8 と tx-hold-pool20 は、ops_per_s ≒ max_open ÷ hold(100 ms)か(8 なら 80、20 なら 200)。in_use_avg、wait_count、p99 も読む。errors の種類(mysql-1213 デッドロック、1205 ロック待ちのタイムアウト)も。

値は、繰り返しの中央値 [最小–最大]。

`proxy_*` 列は CloudWatch の 1 分刻みで、前後の run を含む。`aurora_cpu_*` は Enhanced Monitoring の 1 秒値を run の区間(最初の 20 秒を除く)で切ったもの。`threads_*`、`aurora_questions_per_s` は Aurora に直接つないで 1 秒おきに取ったもの。
